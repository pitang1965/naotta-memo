# 0002. 既存メモのAI取り込みは BYOK・ブラウザ直接呼び出しで行う

- ステータス: **廃案(2026-08-18、ADR 0004 により置換)**
- 日付: 2026-08-17

> **廃案の理由(要約)**: 取り込みを「アプリ内でのAI解析」ではなく「**外部で用意した構造化CSVの取り込み**」に
> 切り替えた。AI解析が必要なら**アプリの外**(手元のAIツール)で行い、きれいなCSVだけをアプリに読ませる。
> これにより本ADRの弱点——生の API キーを localStorage に置く/`dangerouslyAllowBrowser` でブラウザから
> 直接LLMを叩く——が丸ごと不要になり、サーバーなし・キーなし・端末内完結の思想がより素直に保てる。
> 詳細は ADR 0004 を参照。以下は当時の記録として残す。

## 背景

導入前にメモアプリ等へ書き溜めた体調メモを一括取り込みする機能(§6.5)は、自由文からの
意味理解(日付表現のゆれ、症状名の抽出、状態の推測)を必要とする。精度を求めるなら LLM 解析が
現実的だが、このアプリは「サーバーを持たない・健康情報を端末内に閉じる」(§6)を基本方針とする。

取りうる選択肢は3つあった:

- **A. ルールベースの簡易パーサー**: サーバー不要だが表現のゆれに弱く精度が限定的。
- **B-プロキシ. LLM 解析 + 最小限のサーバーレス関数**: 精度は高いが、方針に反してサーバーが復活し、
  運用・プライバシーの負担が増える。
- **B-BYOK. LLM 解析をブラウザから直接呼ぶ**: ユーザー自身の API キーを使う。

前提として、このアプリは**個人用・当面は非収益**(広告・サブスクなし)と決定済み。
また Anthropic API は 2024-08 以降 `anthropic-dangerous-direct-browser-access: true`
(SDK では `dangerouslyAllowBrowser: true`)でブラウザからの直接呼び出しを許可している。
"dangerous" の含意は「**共有**キーを配布アプリに埋め込むな」であり、ユーザーが**自分の**キーを
**自分の**端末で使う BYOK は正当な用法。

## 決定

**B-BYOK を採用する。**

1. ユーザーが設定画面に**自分の Anthropic API キー**を入力し、端末内(localStorage)に保存する。
2. 取り込み時、ブラウザから Claude を**直接**呼ぶ(`dangerouslyAllowBrowser`)。プロキシサーバーは持たない。
3. 解析対象テキストは Anthropic へ送られるだけで、アプリとしてはどこにも保存しない(そもそもサーバーがない)。
4. **人間によるプレビュー確認(取り込む/除外/編集)を必須**とし、AI の解析結果を無確認で保存しない。
5. **ルールベース A は Phase 1 では作らない。** キー未設定時は取り込み画面でキー設定を促すだけ。
6. 将来の画像・スクショ取り込みも、マルチモーダルの同一経路で扱う。

## 結果

**良い方向:**
- 「サーバーを持たない」方針を完全に保ったまま、LLM の高精度が得られる。
- キーも本体データも端末内に留まり、プライバシー姿勢と一致する。
- テキストと画像で取り込み経路を共通化できる。

**代償・要フォロー:**
- ユーザーが自分の Anthropic API キーを取得・入力する手間が要る。個人用(かつ作者は開発者)なら
  許容範囲だが、**非技術者へ配布する段階になれば BYOK は障壁**になる。スコープが変わったら再検討する。
- localStorage に生の API キーが載り、ブラウザからLLMを直接叩く構成は、将来の読み手には
  一見して不穏に映る(本 ADR を残す理由)。キーは"自分のキー・自分の端末"なので許容する。
- 利用コストはユーザー自身のキーに乗る(たまの取り込みなら些少)。
- キー未設定では取り込みが使えない。取り込みは一度きりの移行作業で毎日の導線ではないため許容する。

採用しなかった案:

- **A(ルールベース)**: 精度が低く、キーを入れる単一ユーザーのためにフォールバックを作る価値が薄い。
- **B-プロキシ**: サーバーが復活し §6 の方針に反する。運用・プライバシーの負担も増える。
