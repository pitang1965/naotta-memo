# 0007. 紹介ページは静的HTML1枚として `/about` に置き、アプリはルートに留める

- ステータス: 承認
- 日付: 2026-09-10

## 背景

「なおったメモ」を人に薦められる状態にしたい。ただし主語は作者ではなく**利用者**である。
`display: standalone` のPWAはURLバーを持たないため、ホーム画面から起動している利用者は
**アプリのURLを見ることもコピーすることもできない**。「これ良いよ」と言いたくても渡す手段が無い。
特に iOS ではブラウザのUIが完全に消えるため、共有の手がかりがゼロになる。

一方で、共有先が問題になる。本番 `https://naotta.over40web.club/` はアプリそのもので、
`public/_redirects` が `/* /index.html 200` で全URLをアプリに流している。
このURLを知らない人に渡すと、**説明のない空の記録アプリ**に着地する。

リポジトリのルートには `landing.html` が置かれていたが、`vite.config.ts` にも `package.json` にも
参照が無く、ビルド成果物にも入らない。どこにも配信されていないため更新もされず、
CTA は `準備中` のまま、`<a href>` は1つも無い(=着地しても次に行ける場所が無い)状態で化石化していた。

## 決定

**アプリはルート `/` に留め、紹介ページを静的HTML1枚として `/about` に置く。共有・QRが指すのは常に `/about`。**

- `landing.html` を `public/about.html` へ移す。`public/` に置くことでビルドが必ず拾い、必ず配信される。
  「存在するのに世に出ていない」状態が構造的に起きなくなる。
- 紹介ページは**Reactルートにしない**。`/privacy` `/terms` がアプリ内ルートである先例には**あえて従わない**。
- 紹介ページのQRは実行時に生成せず、**ビルド時に焼いてコミットする**(`scripts/icon/` の既存の流儀)。
  URLは固定で変わらないため、ランタイムのQRライブラリは不要でバンドルは増えない。
  ダーク配色でも読めるよう、**透過させず自前の明るいクワイエットゾーンを焼き込む**。

### なぜルートを動かさないか

`public/manifest.webmanifest` は `"id": "/"` / `"start_url": "/"` / `"scope": "/"`。
アプリを `/app` へ動かすと `id` が変わり、**インストール済みのPWAは別アプリ扱いになる**。
ホーム画面のアイコンは古いURLに取り残される。紹介ページの都合で、既に使っている人の環境を壊す理由は無い。

### なぜReactルートにしないか

`vite.config.ts` のプリレンダーは `outputPath: '/index.html'` **だけ**。`/about` をReactルートにすると
そのページは一切プリレンダーされず、初見の訪問者は `index-*.js`(348KB) + `index-*.css`(38KB) +
`routes-*.js`(21KB) を落とし終えるまで1文字も読めない。紹介ページの唯一の仕事は
**知らない人の最初の3秒**であり、ここを犠牲にはできない。加えて朱印や経過タイムラインの
bespoke CSS 約400行をTailwindユーティリティへ移植すれば、まず確実に劣化する。

## 結果

**良い方向:**
- 知らない人が着地する場所と、使っている人が起動する場所が分かれる。どちらも最適な形で出せる。
- 紹介ページはJSゼロ・1リクエストで描画完了する。
- manifest の `id`/`start_url`/`scope`、Service Worker のスコープ、`shortcuts` の URL、
  アサトモ目覚ましからのディープリンク案 —— いずれも無傷。
- `public/sw.js` は script/style/image/font しか触らずナビゲーションを一切インターセプトしないため、
  `/about` を足しても既存インストール済み端末が古いシェルを掴む事故は起きない。

**代償・要フォロー:**
- **デザイントークンが二重管理になる。** `src/index.css` の `--background` 等は既に
  `landing.html` の `--washi` 等を「相当」としてコピーしたもの。この重複が固定化する。
  片方を変えたらもう片方も手で追う必要がある。
- **人に渡すURLとアプリ本体のURLが違う。** 説明が要る場面が出る。
- **姉妹プロジェクトと流儀が割れる。** アサトモは同じ問題を `https://asatomo.nafuda.me/?intro=true`
  ——ルート＋クエリパラメータ——で解いている。頭の切り替えコストが生じる。
  それでも初回描画の差を優先した。
- パス名 `/about` 自体は不可逆ではない。将来変えたくなれば `_redirects` に
  `/about /new 301` を足せば、印刷・配布済みのQRは生き続ける(ドメインを変えない限り)。

採用しなかった案:

- **ルートを紹介ページにし、アプリを `/app` へ**: 渡すURLが1本で済み最も素直だが、
  manifest の `id` が変わりインストール済みPWAが孤児化する。取り返しがつかない側の変更。
- **ルートのまま、記録が0件のときだけアプリ内で紹介を出す**(アサトモの `?intro=true` 方式):
  URLは1本で済むが、初回描画が上記のバンドル待ちになる。また「もう使っている人に紹介ページを
  見せられない」ため、人に薦める用途に使えない。
- **紹介ページを `/about` のReactルートとして書き直す**: デザインの一貫性とアプリへの
  クライアント遷移は得られるが、初回描画を失う。
